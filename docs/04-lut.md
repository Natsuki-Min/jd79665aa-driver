# 04 · R20 波形表

原厂全刷要 15 秒，是因为它执行一张很长的内置波形。R20 允许我们自己写一张 2048 B 的表，让同样的 DRF 用更短的波形跑完。这一章讲这张表**怎么编码**，以及哪些地方还不能碰。

> 这一章是“能读懂、能生成状态”的级别，不是“照抄就能得到合格画质”的配方。完整原厂表虽然已经从 MTP 解出来，但还没有整表回灌做真机复现。

## 1. 先进入寄存器 LUT 模式

正常初始化用：

```text
PSR (00) = 4B 69
```

PSR 第二个参数的 bit 7 选择 LUT 来源：`69` 中该位为 0，使用内部波形；置 1 后的 `E9` 使用寄存器 LUT。研究/自定义路径会用：

| 值 | 用途 |
| --- | --- |
| `4B 69` | 正常，用内部/原厂波形 |
| `4B E9` | 研究，寄存器 LUT |
| `4B F9` | 短片路径，寄存器 LUT + VCMZ |

然后用 `20` 命令写表：

```text
20 + 2048 B
```

注意：

- R20 连续写地址按 **2048 B 回绕**；写超了会覆盖前面的内容。
- 短写会**保留**旧内容。要得到一张干净的表，先把 2048 B 全填成 `FF`（逻辑 0 的 wire 值），再覆盖需要的状态。
- 写表不等于刷新；真正动像素还是 `12`（DRF）。

## 2. 逻辑字节 → 线上字节

R20 的字节不是直接写逻辑值，而是先取反、再按固定顺序重排：

```text
逻辑 bit：0 1 2 3 4 5 6 7
线上 bit：4 7 6 1 0 3 2 5

wire = 0xFF XOR permute(logical)
```

单 bit 对照：

| 逻辑值 | 0 | 1 | 2 | 4 | 8 | 16 | 32 | 64 | 128 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| wire（hex） | `FF` | `EF` | `7F` | `BF` | `FD` | `FE` | `F7` | `FB` | `DF` |

这层关系由时长单比特实验、组合计数、ADC 相位位置和有限序列共同验证。它只用于 R20，不要套到图像数据、普通寄存器或整份 MTP 上。

`host/lut_codec.py` 里就是 `encode_byte()` / `decode_byte()`：

```python
from lut_codec import encode_byte, decode_byte

assert encode_byte(0x00) == 0xFF
assert decode_byte(0xFF) == 0x00
assert encode_byte(0x01) == 0xEF
```

## 3. 一张表的结构

```text
偏移 0..6      7 字节头部
偏移 7          H0 首状态
偏移 95         H1 首状态
偏移 183        H2 首状态
偏移 271        H3 首状态
偏移 359        H4 首状态
偏移 447        H5 首状态
```

首状态公式：

```text
H 的首状态偏移 = 7 + 88 * H
```

每个入口按经验步长 11 B 排列状态。535 B 的表就是：

```text
7 + 6 * 8 * 11 = 535
```

即每条入口 8 个状态。**不要**把“入口间距 88 B”直接当成六个物理隔离的 bank；它只是当前工作模型。

六条入口的已验证作用：

| 入口 | 作用 |
| --- | --- |
| H0 | 电平码可改变所接 VCOM 测试点；切换码有额外约 21 ms |
| H1 | RAM 像素码 `00`；首状态有特殊行为 |
| H2 | RAM 像素码 `01` |
| H3 | RAM 像素码 `10` |
| H4 | RAM 像素码 `11` |
| H5 | source 供电 Mode0/Mode1 选择；高位用途未知 |

## 4. 一个 11 B 状态

| 相对字节 | 字段 | 含义 |
| ---: | --- | --- |
| 0 | G | 外层重复；0 终止这条路径 |
| 1 | ABC_levels | A/B/C 的 2bit 电平码（bits 7:6、5:4、3:2）；bits 1:0 未知 |
| 2 | DEF_levels | D/E/F 的 2bit 电平码；bits 1:0 未知 |
| 3 | A | A 相帧数 |
| 4 | B | B 相帧数 |
| 5 | C | C 相帧数；只验证低 7 bit |
| 6 | RA | ABC 子组重复 |
| 7 | D | D 相帧数 |
| 8 | E | E 相帧数 |
| 9 | F | F 相帧数；只验证低 7 bit |
| 10 | RB | DEF 子组重复 |

执行顺序：

```text
repeat G:
    repeat RA: A -> B -> C
    repeat RB: D -> E -> F
```

扫描数：

```text
N = G * ((A + B + C) * RA + (D + E + F) * RB)
```

例：`G=3`，`A/B/C=2/3/4`，`RA=2`，`D/E/F=1/2/3`，`RB=3`：

```text
N = 3 * ((2+3+4)*2 + (1+2+3)*3)
  = 3 * (18 + 18)
  = 108
```

这和实测的 108 扫描、50 Hz 档约 2.219 s 对得上。

2bit 电平码的粗略含义（像素轨）。控制器侧名字和这块板上的丝印一起列出：

| 码 | 逻辑名 | 板载丝印 | 档位 | 现象 |
| ---: | --- | --- | --- | --- |
| `00` | L00 | — | 接近 0 V / 保持 | 低场短时近似保持；不是通用 HiZ |
| `01` | L01 / VSP | VSH1 | 强正档 | 白/黄被往黑拉，容易变暗 |
| `10` | L10 / VSN | VSL | 负档 | 黑变浅、红偏黄，依赖初态 |
| `11` | L11 / VSPL | VSH2 | 较弱正档 | 较慢变暗，过渡色受预处理影响 |

丝印对应：

```text
VSP  = VSH1
VSPL = VSH2
VSN  = VSL
```

颜色按电荷排（目前是“几乎确认”的工作模型，不是直接测到的电荷量）：

| 颜色 | 电荷 |
| --- | --- |
| 黑 | 强正 |
| 红 | 弱正 |
| 白 | 弱负 |
| 黄 | 强负 |

注意：这里说的是**颜色颗粒的净电荷排序**；VSP/VSN 是驱动电压轨的名字，两者不是同一个“正负”。

方向上也对得上：正电场把白/黄往黑拉，负电场把黑往浅拉；红/黄是中间态，最终颜色还受初态、剂量和保持影响。

## 5. 两个容易踩的边界

### 5.1 G=0 是终止，不是“执行 0 次”

`G=0` 会挡住后续活动状态，让这条路径结束。实测里它常常只花不到 1 ms。

但“非零 G、所有时长/重复为 0”的空状态**仍可能产生额外扫描**。所以：

- 用 G=0 做终止；
- 不要拿 `N` 公式无条件算空状态；
- 想跳过某条入口，最稳的是让它终止，而不是塞一堆 0。

### 5.2 H1 首状态是特例

在头部第 7 字节（R20[6]）逻辑为 `00` 时，H1 的第一个状态即使给完整 24 帧和 G 重复，也常常只跑约一帧。

已知的实用处理：

1. 给 H1 放一个**一帧空状态前缀**，有效状态放到下一项；
2. 或者干脆**不用 H1**，视频路径就是用 H2/H3 表示新黑/新白。

后续实验还发现：把 R20[6] 设成非零（例如逻辑 `01`）能在已测条件下让 H1 首槽的 A/B 计数恢复；但这不是“bit0 专用使能”，`02/03/04/08/10/20/40/80` 也都有效，而且 A=B=0、只开 C/D/E/F 时仍可能只跑一帧。**所以不要把它当成已经解释清楚的普通状态。**

## 6. 用工具生成状态

`host/lut_codec.py`：

```python
from lut_codec import pack_state, unpack_state

# G=3, 六相电平全 0..3, 帧数 A..F, 两个子组重复
wire = pack_state(3, [0, 1, 2, 0, 1, 2],
                  [2, 3, 4, 1, 2, 3], [2, 3])
info = unpack_state(wire)
print(info["scheduled_scans"])   # 108

# 放到 H2 的首状态（偏移 7+88*2 = 183）
table = bytearray([0xFF] * 2048)  # 逻辑 0 的 wire 值
table[183:183 + 11] = wire
```

但**头部 7 字节不能随便填**。头部的完整功能还没解开；H1 又依赖 R20[6]。所以上面的代码只演示“怎么放一个状态”，不是一张能直接跑的完整表。

## 7. 原厂表在哪、能不能直接用

MTP 里解出的 `profile-01` 就是和这块屏实测吻合的那张 742 扫描表：

```text
header: 00 22 24 78 22 00 08
```

它与历史实测的已辨识位一致，为解码结果提供了独立支持；代表表中的一处等价差异见 [详细对照](05-mtp.md#profile-1-和实测对上了什么)。但是：

- 535 B 只是表块，不是完整 2048 B；
- 整表没有回灌做过 BUSY/VSL/光学复现；
- wrapper、选表规则、未知尾部还没解释；
- 所以**不要**把 `profile-01` 当成“已经验证的固件”直接上传。

MTP 的细节见 [05-mtp.md](05-mtp.md)。

## 8. 还没解决的

| 问题 | 现状 |
| --- | --- |
| 头部 7 字节完整功能 | 只知道 R20[6] 与 H1 首槽有关；其余未知 |
| 电平字节 bits 1:0 | 没看到新增平台，用途未知 |
| C/F 时长 bit 7 | 没找到保持功能，也没排除其他作用 |
| 六入口真实 bank 结构 | 写地址回绕已证，物理 bank 未证 |
| 每轨有效状态数 | 8 个是当前工作模型，不一定是硬件上限 |
| R21–R24 | 多个条件下阴性；不证明无效 |
| 完整原厂波形回灌 | 未做 |
