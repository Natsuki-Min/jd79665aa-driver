# 02 · 初始化与全刷

这一章是“让屏正常显示一张四色图”的最小路径。`driver/src/epd.c` 就是它的实现，`driver/src/main.c` 负责画测试图。

## 1. 复位

```text
RST HIGH 20 ms
RST LOW   2 ms
RST HIGH 20 ms
等待 BUSY 变高，最长 3 s
再等 30 ms
```

复位后需要等待 BUSY 变高。示例驱动将此等待设为最多 3 秒，超时返回失败，使调用方可以识别复位阶段没有完成。

## 2. 初始化寄存器

这套序列来自已工作的上游驱动，并在 A1 实物上使用。部分参数数量和值与公开 AA 资料不同，因此移植时先保留这个可运行基线，再将变动的寄存器分别作对照。

| 命令 | 参数（hex） |
| --- | --- |
| `AA` | `49 55 20 08 09 18` |
| `01` | `3F` |
| `00` | `4B 69` |
| `05` | `40 1F 1F 2C` |
| `08` | `6F 1F 1F 22` |
| `06` | `6F 1F 14 14` |
| `03` | `00 54 00 44` |
| `60` | `02 00` |
| `30` | `08` |
| `50` | `3F` |
| `61` | `03 20 02 58` |
| `65` | `10 00 20 00` |
| `E3` | `2F` |
| `84` | `01` |

说明：

- `61` 是 800×600：`03 20` = 800，`02 58` = 600。
- `00` 的第二个参数 `69` 选择正常 LUT；研究/自定义波形会改用 `E9` 或 `F9`，见 [04-lut.md](04-lut.md)。
- `30 = 08` 含动态帧率设置；扫描周期可能随内部配置变化。后续固定频率实验使用的是另一组明确的 PLL 设置。
- `AA` 在此序列中发送 6 字节；这就是当前实现的命令长度，与公开表的差异保留为版本核对项。

## 3. 全刷流程

```text
epd_init()                  // 复位 + 上表初始化
epd_power_on()              // 04，等 BUSY
R83 全窗                    // 00 00 03 1F 00 00 02 57 01
10 + 120000 B               // DTM，整帧数据，CS 连续低
R83 全窗                    // 再设一次
12 00                       // DRF，等 BUSY
02 00                       // POF，等 BUSY
```

全窗 R83 的 9 个字节：

```text
00 00 03 1F 00 00 02 57 01
```

- `0000`..`031F` = x 0..799
- `0000`..`0257` = y 0..599
- 最后 `01` 是原厂全窗参数里的值，本项目按已验证值发送，没有单独解释它的全部含义。

`driver/src/epd.c` 里对应：

- `epd_init()`：复位 + 初始化表
- `epd_power_on()`：`0x04`
- `epd_write_frame()`：设全窗 + `0x10` + 120000 B
- `epd_refresh()`：再设全窗 + `0x12` + 等 BUSY
- `epd_power_off()`：`0x02`

## 4. 实测时间

这些是这块屏上的历史实测，不是规格书保证值：

| 阶段 | 时间 |
| --- | --- |
| PON | 约 118 ms |
| 120000 B 数据传输（1 MHz） | 约 1149 ms |
| DRF（原厂全刷波形） | 约 15.145–15.25 s |
| POF | 约 62 ms |

所以一次完整“初始化 + 全刷”大约 **16–17 秒**。其中主要耗时来自原厂波形。固定 PLL 曾将其缩短到约 6.38 s；进一步的视频级实验使用短自定义波形，两条路线的结果见 [快刷实验](06-refresh-experiments.md)。

## 5. BUSY 怎么读

- **低 = 忙，高 = 空闲。**
- 只看到“高”不够：如果命令根本没被接受，BUSY 也可能一直是高。驱动会记录有没有出现过下降沿；如果没有，会打印：

```text
WARN [REFRESH]: no BUSY LOW observed; HIGH alone does not confirm panel response
```

这表示等待函数观察到高电平，但没有捕获本次命令引起的忙脉冲。`DONE` 表示软件流程返回成功；BUSY 是否实际响应、图像是否显示，可结合日志与面板观察核对。

- 示例程序对 PON、DRF、POF 的等待上限设为 120 秒，这是软件超时值。
- 任一步失败后，示例会尝试 POF 并复位，再返回串口控制台，方便下一次重新初始化。

## 6. 构建与烧入

```sh
cd driver
./build.sh
```

生成：

```text
driver/build/epd_bringup.uf2
```

按住 Pico 的 BOOTSEL 接入 USB，把 UF2 复制到 `RPI-RP2`。上电后：

- 画黑/白/黄/红四条竖带 + 边框 + 两个不对称角标；
- USB 串口输出每一步的 BUSY 日志；
- 输入 `r` 重画，`s` 看状态。

串口（设备名可能不同）：

```sh
# 使用 miniterm 需要另装 pyserial；screen 是另一种选择
python3 -m serial.tools.miniterm /dev/ttyACM0 115200
# 或者
screen /dev/ttyACM0 115200
```

## 7. 常见坑

1. **只发 768×552 的数据。** 全刷 DTM 要 800×600×2bpp = 120000 B。少发会错位/花屏。
2. **忘了第二次 R83。** 原厂流程在 DTM 之后、DRF 之前会再设一次窗口。基础驱动照做了。
3. **CS 抬早了。** Pico SDK 的 `spi_write_blocking()` 会在返回前排空发送 FIFO 并等待 SPI 空闲；本驱动在它返回后才抬 CS。
4. **DC 事务混在一起。** 参考驱动用分开的 CS 事务发送命令和参数，移植时保持相同事务边界便于核对。
5. **拿 15 秒当故障。** 原厂全刷就是十几秒；看 BUSY 有没有正常下降/上升，而不是看总时长。
6. **将多个变量一起改动。** 图像长度、窗口位置、SPI 事务和初始化参数分别核对，更容易定位是哪一层影响了显示。
